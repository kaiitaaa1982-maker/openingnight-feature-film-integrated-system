# 要件定義

工程を作る・直す前と、テストを足すときに読む。守れる部分は `test/requirements-trace.test.mjs` が検査する。

## 2段の要件

| 段 | 置き場所 | 中身 |
|---|---|---|
| プロダクトの要件 | `docs/requirements/README.md`（1枚） | 目的・使う人と役割・9領域・業務の一周と領域の対応・やらないこと |
| 工程の要件 | `docs/requirements/<領域>/<工程>.md`（工程ごとに1枚） | 下の形 |

- 要件には「何を」と「何をもって完成とするか」だけを書く。「なぜそう決めたか」は brain に書き、要件からリンクする
- 工程の受け入れ基準の正本は要件の機能要件。会社ルートの `plans/` の計画には要件の文を書き写さず、「FR 番号 → テスト」の対応表だけを書く。計画の香盤表の受け入れ基準は作業（タスク）の完了条件で、工程の基準は FR 番号で指す（計画の型は会社ルートの `plans/README.md`）
- 要件は、コードと同じ PR で直す。要件とコードが食い違ったら、どちらが正しいかを代表に確かめる（推測で片方に合わせない）

## 工程の要件の形

冒頭に frontmatter（`domain`・`process`・`code`・`status`）と、brain の業務手順へのリンクを置く。`status` は「下書き」「確定」「廃止」のどれか（括弧で補足を足してよい）。代表が要確認に答えて確定するまでは「下書き」で、レビューでは下書きの要件との食い違いを P0 ではなく P1 として挙げ、代表に確かめる。続けて次の節を書く。

1. **ユーザーストーリー** — 誰が・何をしたいか。優先度（P1〜）をつける
2. **受け入れシナリオ** — 前提と結果だけを書く。画面の操作手順は verify の `features/` に書く
3. **機能要件** — `## 機能要件` の節に次の表で書く（検査はこの節の表だけを読む）。1行1要件、「〜すること」で終える
4. **テストの穴** — 状態が「テスト」でも、テストがまだ確かめていない点（任意。レビューで見つけたら書く）
5. **成功基準** — 数で確かめられるもの（件数・時間）
6. **前提とやらないこと**
7. **要確認** — 業務としてどうあるべきか決まっていないことを、問いとして番号つきで書く。代表が決めたら、機能要件の表に番号を振って足す

```
| ID | 要件 | 状態 | 確かめる所 |
|---|---|---|---|
| FR-PROD-SCHED-004 | 〜すること | テスト | `test/workflow-routes.test.mjs` |
```

## 番号の決まり

- 形は `FR-<領域>-<工程>-<3桁>`。工程の中の連番なので、別のブランチで別の工程を進めても衝突しない
- 領域の略号: 企画 `PLAN`・制作 `PROD`・営業 `SALES`・宣伝 `PUB`・売上 `REV`・経費 `EXP`・精算 `SETL`・会計 `ACCT`・台帳 `LEDG`・共通基盤 `CORE`・管理 `ADMIN`。工程の略号は frontmatter の `code`（例: 日程の確定は `SCHED`）。frontmatter の `domain` はフォルダ名と同じにする
- 番号は、決まった要件にだけ振る。決まっていない問いは要確認の節に置き、番号を使わない
- main に入った番号は振り直さない。やめた要件は行を消さず、状態を「廃止」にする
- 1つの要件を分けるときは、新しい番号を振り、古い行を「廃止」にして「確かめる所」に行き先の番号を書く

## 状態と、確かめる所

| 状態 | 意味 | 検査が見ること |
|---|---|---|
| テスト | 自動テストで、要件の主な点を確かめている | 「確かめる所」に挙げた `test/…test.mjs` があり、そのテスト名（`test`・`it` の第1引数。skip・todo は数えない）に番号が出てくる |
| 画面 | verify で画面を動かして確かめる | その番号が core の `.claude/skills/verify/features/` の機能の地図か手順（`README.md` と `_` で始まる共通部品を除く）に出てくる |
| 未検証 | 振る舞いはあるが、確かめる所がまだ無い（返すべき借り）。確かめる所には、その振る舞いがある実装の場所（`src/…`）を書く | 何も見ない。テストか `features/` を足したら状態を変える |
| 廃止 | やめた | テストと `features/` に出てこない |

- 状態が4つのどれでもなければ落ちる
- テスト名には番号をそのまま入れる。1つのテストが複数の要件を確かめるなら、番号を並べる（例: `test('FR-PROD-SCHED-004 FR-PROD-SCHED-007 2話持ち…', ...)`）
- 番号がテスト名にあるだけでは足りない。要件の主な点を assert していなければ「未検証」にし、一部だけなら「テストの穴」に書く
- 逆向きも見る。テストや `features/` に出てくる番号がどの要件にも無ければ、また要件のファイルに書いた番号が機能要件の表に無ければ落ちる（打ち間違いを防ぐ）

## 既存の要件文書

`docs/` にある領域ごとの要件・設計の文書は、一度に書き直さない。その工程を組み直すときに、この形の工程の要件へ移し、古い文書は参照として残す。
