# データベース

表の定義・移行・SQL を書くときに読む。間違えると取り返しがつかない領域なので、決まりを絞る。
守れる部分は `test/database-rules.test.mjs` と `npm run ci:migrations` が検査する。
SQL は D1 と PostgreSQL の両方で動く形で書く（SQLite だけの形を新しく書かない。`dialect.md`）。

## 移行の決まり

- main に入った移行ファイル（`migrations/`）は書き換えない。直すときは次の番号の移行を足す。入った移行の中身は検査が指紋で守る
- 番号は4桁の連番で、抜けも重複も作らない。表の変更は1本ずつ入れ、同時に作業するブランチで同じ番号を作らない
- 本番は戻さず前へ直す。消す・名前を変える移行は避け、足すだけの形にする（古い Worker に戻しても動くように）
- 移行を足したら `migration-manifest.json` の表・トリガー・索引の数を直し、`npm run ci:migrations` を通す
- 既存の表へ UNIQUE や NOT NULL を足す前に、違反する行が無いかを読むだけの問い合わせで確かめる
- 移行を main に入れる PR で、検査の指紋の一覧（`test/database-rules.test.mjs`）に足す。本番へ当てるのは代表（D-005）

## DB が守るもの・アプリが守るもの

判断の基準: 画面を通らない書き込み（一括取込・スクリプト・バグ）でも、絶対に破れてはいけないか。はいなら DB の制約、いいえならアプリに置く。

| DB（制約・トリガー）で守る | アプリ（routes）で守る |
|---|---|
| 一意性（UNIQUE）・参照（外部キー）・値の範囲（CHECK）。例: 税込＝税抜＋税額 | 誰がどの行を見られるか（組織と権限） |
| 同時に書いたときに破れる約束（`transaction_guards` で batch ごと止める） | 業務の流れの順番 |
| 確定した記録を後から書き換えない（トリガーで拒否） | 外部サービスとの整合 |

## 組織の境界

- 業務の表の読み書きは、必ず `org_id` で絞る。別の組織の行が見える・書けるのは P0 の欠陥
- 組織と権限は、サーバーが Cookie と Access の検証から決めた値（`c.get('identity')`）だけを使う。画面から届いた組織 ID を信じない

## 値の持ち方

- 金額・率の列の型と名前、整数の強制（typeof の CHECK）、金額の計算は `money.md` に従う。税抜・税額・税込は3つとも持ち、片方から計算しない
- わからない値は NULL か `unverified` で持つ。0 や空文字で埋めない
- 状態は上書きせず、日付つきの行を足して現在の状態を導く（版・取消は別の行）

## D1 の上限

1文の値の数・1回の batch の文の数・1つの値の大きさに上限がある。数は `README.md` の「売上基幹の架空データ」と `src/d1-limits.mjs` が正本。
大きな保存は、表ごとに複数行の INSERT にまとめ、上限を超えない大きさに分ける。
