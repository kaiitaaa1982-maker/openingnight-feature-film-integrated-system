# レビュー

実装を終えて draft の PR を開き、確かめ役に渡すとき、またはレビューを頼まれたときに読む。開発の流れ（8ステップ）のどこを誰が持ち、どこで止めるかを確かめるときにも読む。

## 8ステップ

通常の PR は、次の8ステップを順に踏む。書籍『プロフェッショナルAI駆動開発』第7章の開発フローを、このリポジトリの置き場・役・止める所に写したもの。計画（会社ルートの `plans/`）が「8ステップ」と言うときは、この表を指す。役の名前は、会社ルートの `.agents/ai-roles.json`（D-038）の役。

| Step | 内容 | 置き場・成果物 | 役 | 次へ進む条件 |
|---|---|---|---|---|
| 1 | 計画 | 会社ルートの `plans/<名前>.md`（目的・決めること・香盤表・やらないこと・決定ログ。型は `plans/README.md`。仕組みの8点は `align-request` の手順で、計画の「仕組みとして」の節に書く）と、工程の要件 `docs/requirements/<領域>/<工程>.md`（`requirements.md`） | `plan`（計画役のモデル） | 代表が合意し、計画を仕様書に格上げする。決まっていない業務の問いは推測で埋めず、要件の要確認か計画の裁定待ちに置く |
| 2 | 計画の AI レビュー（仕様・設計） | 計画と要件への指摘（P0〜P2。重さは下の表と同じ）。直しは計画の決定ログに残す | `review`（計画の書き手の 計画役のモデル と別のモデル。Opus か Sonnet） | P0・P1 を計画に反映する。見るのは、要件や決定との食い違い、置き場と依存の向き（`architecture.md`）、DB・SQL・金額（`database.md`・`dialect.md`・`money.md`） |
| 3 | 計画の AI レビュー（試験の網羅） | 計画の「FR 番号 → テスト」の表と、要件の機能要件の「確かめる所」 | `review`（Step 2 に混ぜず、別の回で試験だけを見る） | 主な正常系・異常系・境界が試験に載り、期待値の出所が要件になっている（`testing.md` の「書き方」）。業務でどの異常が重いかは推測せず代表に確かめる |
| 4 | 実装 | `claude/*` のブランチと、1つの作業場（`C:/ONwt/<名前>`）。要件とコードは同じ PR | `implement`（Opus か Sonnet。香盤表の配役欄で選ぶ） | 失敗する試験を先に書く。計画の「やらないこと」と、このフォルダのルールを破らない |
| 5 | 試験を全部通す | 手元は `testing.md` の「流し方」の「PR の前（作り手）」の段を流す（移行は `npm run ci:migrations`）。push して draft の PR を開き、CI を流す | 実装した役（直しは `fix`） | 失敗0。試験を弱めて通さない（`testing.md` の「骨抜きの禁止」）。借りの一覧（`test/*-debt.json`）が増えない。試験の本数が減らない |
| 6 | 実装の AI レビュー | この文書の「いつ」「観点」「指摘の重さ」「終わる条件」 | `review`（実装と別のモデル）→ `final-review`（Opus）。画面や動きを変えたら verify（`e2e`） | P0・P1 が0件。最後の head SHA の CI の結果を PR に書き、Opus の最後の確かめを終える。直したら Step 5（試験と CI）から流し直し、Step 6 に戻る |
| 7 | 人のレビュー | PR | 代表 | 設計判断と業務との整合を見て、PR ごとにマージを許可する。マージは代表が行う |
| 8 | テスト駆動のリファクタリング | 通常は別のブランチと PR。ループのターン内のリファクタリングは同じブランチで行う。ファイルの移動を含むなら、`architecture.md` のとおり改修と別のブランチにする | `implement`（Step 4 と同じ基準） | 観点・対象・担保を1つずつに絞る（例: 観点＝借りの返済、対象＝1つのフォルダ、担保＝前後で同じ緑の試験）。振る舞いを変えない。借りの一覧は減るだけで増えない |

同じ種類の指摘が Step 6 で2回出たら、下の「指摘を仕組みへ戻す」に従って検査かルールへ上げる。

### ループ（`/goal`）との対応

mizchi「俺のAIプログラミング手法」（Zenn、2026-10-05）の、数の指標で目標を決め、満たすか上限に当たるまで繰り返す型を取り入れたもの。8ステップのうち Step 4〜6 と 8（実装・試験・確かめ・リファクタリング）だけを回し、ループを止めるかどうかは `goal_check` の数で決める。Step 1・2・3・7 はループに入れず、代表と `plan`（計画役のモデル）が持つ。手順の細目は、会社ルートの `plans/2026-10-08-loop-and-exception-ux.md` の「ループの回し方」にある。

| ループの手順 | 8ステップ | 持ち主 |
|---|---|---|
| 目標を書く（`goals/<名前>.md`: 守る指標・伸ばす指標・上限・人へ上げる変更） | Step 1〜3 の成果物に含める | 代表と `plan` |
| 指標を数で出す（`npm run metrics -- --goal goals/<名前>.md` が JSON と PASS/FAIL を出す） | Step 5 の合否を数にしたもの | `implement` |
| `/goal` で回す | 毎ターン Step 4 → 5 → 6 → 8 | 実装は Opus のセッション。確かめは Sonnet のサブエージェント（`model: sonnet`） |
| 終わったら draft の PR | Step 6 の続き（`review` → `final-review`）と Step 7 | `review`、`final-review`、代表 |
| 探索の巡回（月1回、代表が起動） | 次の goal の材料（Step 1 へ戻る） | 代表が採る項目を選ぶ |

- 指標は、同じコミットで2回流して同じ値になるものだけにする。時間のように揺れる値は `goal_check` に使わない。`/goal` の判定は会話を読む小型モデルが行うので、判定の材料は `goal_check` の出力だけにする
- 上限は20ターン。指標が2ターン続けて動かなければ止める。上限と止める条件の無いループは始めない
- 人へ上げる変更（migrations・権限・金額の丸め・計算式・試験や性質を弱める変更）を含むターンはループを止め、Step 7 の代表に渡す。指標を緑にするために試験や性質を弱めない
- ループで直すのは、計画の香盤表で配役が Opus のタスクのファイルだけ。画面・文言の直しはループの外で、通常の PR として Step 1〜8 を順に踏む。ループのターン内の Step 8 は同じブランチで行い、ファイルの移動は含めない（移動は別のブランチで通常の PR にする）
- 毎ターンの確かめ（Sonnet）で、終わったあとの `final-review` を置き換えない
- `goals/` の型と `npm run metrics` ができるまで、ループは回さない

## いつ

- 作り手は確かめ役に渡す前に draft の PR を開く。`ci.yml` は PR を開く前のブランチへの push では走らない。実装したセッションとは別のセッション（またはサブエージェント）で確かめる
- **実装と別のモデルが先、Opus が最後**（D-038 の追記、2026-10-04・2026-10-09）。先に会社ルートの `.agents/ai-roles.json` の `review` の役（実装が Opus なら Sonnet、Sonnet なら Opus。読むだけ）がダブルチェックする。対象の作業場を書き換えず、コミット・push もしない。直しは `fix` の役へ渡す
- 確かめ役は draft の PR の **head SHA の CI が終わるまで待ち**、その SHA の結果と省いた本の理由を読む。結果が無い・実行中を緑と読まない
- 試験の全体を流し直さず、変えたファイルだけをわざと壊すか、新旧に同じ操作を流して比べる。読むだけの役の反証は一時のコピーやメモリ上で行い、対象の作業場に変更を残さない。壊したのに関係する本が落ちなければ **P1（テストの抜け）** とする
- 最後は `final-review` の役（Claude Opus）が確かめる。受け持つのは金額・権限・移行・SQL・DB の入口・試験の土台に触れる変更と、代表にマージを頼む前。確かめ役のダブルチェックで最後の確かめを置き換えない
- 次の観点を1つずつ順に流す（並列に起動すると使用量の上限で全部止まることがある）
  - いつも: 境目・異常系（`edge-case-reviewer` の観点）
  - 工程の要件か計画があるとき: 要件・計画とのずれ（`plan-reviewer` の観点）
  - 権限・SQL・ログ・`migrations/`・`*-store.mjs` に触れたとき: 安全（`security-reviewer` の観点）
- 観点の定義は core の `.claude/agents/`（既定 `model: sonnet`）。実装が Sonnet のときは、呼ぶ側がサブエージェントの model を opus で上書きする。`.codex/agents/` と本文をそろえる決まりは、Codex に戻すときのために残す
- レビューする側には、差分（`git diff origin/main...HEAD`）と、このフォルダのルールと、該当する工程の要件（`docs/requirements/`）と計画（会社ルートの `plans/`）だけを渡す。実装の経緯は渡さない
- P0・P1 を直したら、もう一度レビューに戻す

会社ルートで表を確認し、レビューの対象の作業場と、上記の材料・観点だけを書いた依頼ファイルを渡す。

```sh
python ops/ai_route.py show
python ops/ai_route.py run --role review --model sonnet --cwd <作業場> --prompt-file <依頼> --out <結果>
```

Claude の役では、2行目は使うモデルの完全な ID を表示して終了コード3で返る。その ID でサブエージェントか `claude -p --model <ID>` を起動する。

## 観点

1. 要件と計画とのずれ: 工程の要件の機能要件（状態・確かめる所）と計画の「FR 番号 → テスト」の表に、対応する変更とテスト名があるか（不足）。どちらにも無い変更が混ざっていないか（過剰）。工程の要件が無い作業（ファイルの移動・地図の更新など）は、計画の香盤表の受け入れ基準と「やらないこと」で照合する
2. 誤りと異常系: 分岐の漏れ、境界（0・上限・ちょうど）、空・未確定（`unverified`・NULL）の扱い、失敗したときの経路
3. 権限と秘密: 別組織・権限の無い人のデータが見えないか。秘密値・個人情報をログや画面に出していないか
4. ルールとの違い: `docs/rules/` の該当ルール（計算と DB の分け方、骨抜きテスト、SQL の方言（`dialect.md`））。借りの一覧（`test/*-debt.json`）に足した数が無いか、動かしただけなら合計が増えていないか
5. お金の正しさ（`money.md`）: 整数円・符号・端数の行き先・税抜と税込の関係。会計の数字は二重に数えていないか

## 指摘の重さ

| 重さ | 意味 | 扱い |
|---|---|---|
| P0 | データを壊す・権限が漏れる・金額や機能が誤る | 直すまでマージしない |
| P1 | 誤りの芽・テストの抜け | 直す。直さないなら理由を PR に書く |
| P2 | 名前・書き方 | 余裕があれば直す。無ければそのままでよい |

指摘には `ファイル:行` と、壊れる入力の例を添える。

## 終わる条件

- P0・P1 が0件なら合格
- 代表にマージを頼むのは、最後の head SHA の CI が終わり、その結果を PR の本文かコメントに書き、Opus の最後の確かめを終えてから。CI は記録のみでマージを止めないので、終了前に頼まない
- 往復は、単純な変更なら1回、複雑な変更でも3回まで。それでも指摘が行き来するなら、代表が決める
- 差分を読むレビューでは、画面の崩れ・無限の読み込み・状態の取り違えは見つからない。画面や動きを変えたら、最後は verify で実際に動かして確かめる
- マージは代表が行う

## 指摘を仕組みへ戻す

- 同じ種類の指摘が2回出たら、検査かルールへ上げる。先に検査（`test/*-rules.test.mjs`）で守れないかを考え、守れない部分だけをルールに書く（`README.md`）
- 要件と実装の食い違いを見つけたら、推測でどちらかに合わせず、代表に確かめる（`requirements.md`）
